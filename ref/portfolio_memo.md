# ポートフォリオ概要
###CanSat屋内データロガー：降下検知と高信頼性通信の実証

## 概要
本プロジェクトは、衛星オンボードソフトウェア開発へのキャリアチェンジを目指すにあたり、組込みシステムの基礎技術を実践的に習得するために制作した卓上CanSat（模擬小型探査機）モデルです。Seeed Wio Terminalを用い、気圧センサーによる降下フェーズの検知と、通信が途絶した状況下でのデータ保全という、実際の衛星・探査機システムに共通する2つの課題に取り組んでいます。
## 着眼点
自宅アパートという限られた環境では、実機CanSatのような屋外での打ち上げ・落下実験はできません。そこで、本プロジェクトでは「正確な物理量の再現」ではなく「センサー値の変化を検知し、システムが正しく状態遷移すること」に焦点を当てています。また、自宅Wi-Fiの電波が届かない区間が発生することを、通信障害シナリオとしてそのまま活用し、SDカードへのバッファリングと復帰後の自動送信という、高信頼性通信の基礎的な仕組みを実装・検証しています。

## 実装内容（概要）
気圧センサー（BMP280）による降下検知ロジック
状態遷移管理（待機・降下中・通信断・復帰・着地）
Wi-Fi通信断時のSDバッファリングと復帰後の自動再送
Python（pandas/matplotlib）によるログの可視化・解析
（発展）Rustへの一部処理移植、組込みRust環境構築への挑戦

4. センサー仕様と閾値（気圧・IMUの閾値、判定ロジック）
### 降下検知ロジック（シンプル版）
####採用する方式：移動平均との差分による閾値判定
複雑な微分計算や変化率（hPa/秒）を計算せず、「直前の気圧値」と「現在の気圧値」を一定間隔で比較するだけのロジックにします。

#### 具体的な考え方

一定間隔（例：1秒ごと）で気圧を取得し、直近数回分の平均（移動平均）をベースラインとして保持する
新しい気圧値が、ベースラインから一定値（閾値）以上下がったら「降下中」と判定する
気圧が再び安定（変化がほぼゼロ）したら「着地」と判定する

baseline = 直近5回分の気圧の平均
現在値 = 今の気圧
if (baseline - 現在値) > 閾値（例：0.3 hPa）:
    状態 = 降下中
elif 変化がほぼない（例：±0.05 hPa以内が続く）:
    状態 = 着地・安定

* 気圧は標高が上がるほど下がりますが、地表付近では概ね「10m上昇するごとに約1.2hPa低下する」という近似が一般的に使われます。
これを1フロア分の高さに当てはめます。

	1フロアの高さ：おおよそ3〜4m（商業施設や市役所だと3.5m前後が目安）
	1フロアあたりの気圧変化：3.5m ÷ 10m × 1.2hPa ≈ 0.4hPa程度

つまり「1フロア分の移動で0.4hPa程度変化する」という見積もりに対して、ノイズの影響を考慮し、やや低めの0.3hPaを「これくらい変化したら降下とみなしてよさそうだ」という仮の閾値として提示しました。

#### 「降下中」であることの見せ方
- タイミング1：実験中（リアルタイム）にその場で示す
実験者（あなた自身）が、エレベーター降下中に「今、降下検知された」とその場でわかる方法です。

LCD画面表示：状態（待機中／降下中／着地）を画面に文字で表示する
LED点灯：Wio Terminal本体にLEDがあれば、状態に応じて色や点灯パターンを変える
ブザー音：状態が変わった瞬間に短い音を鳴らす（Wio Terminalはブザー内蔵）

これらは「その場で確認できる」という手順6の要望にも直結します。

- タイミング2：実験後（事後）にデータとして示す
SDカードに記録したログを、帰宅後にPythonで読み込み、グラフ上で「ここが降下中と判定された区間」を可視化する方法です。

気圧の時系列グラフに、状態（待機／降下中／着地）を色分けした帯（背景色）として重ねる
「判定された降下開始・終了のタイムスタンプ」を別途出力する

5. 通信仕様（Wi-Fi、SDバッファリングの挙動）
6. データフォーマット（ログ形式、CSV項目）
run_id, seq, timestamp, pressure_hpa, baseline_hpa, state

- run_id：その日の計測が何回目か（1回目、2回目、3回目）
- seq：その計測内での連番
- timestamp：起動からの経過時間（ミリ秒、もしくは秒）
- pressure_hpa：気圧の値
- baseline_hpa：その時点の移動平均値（判定の根拠を後から検証できるように残す）
- state：IDLE／DESCENDING／PAUSED／LANDEDのいずれか

#### LCD画面表示
現在の状態（アイドル／アーム済み／記録中／着地）
今回の記録件数（seq数）または記録時間

これにより「記録が正常に取れているか」をその場で確認でき、もし記録できていなければ、その場で同じ展望台で再試行する判断ができます（市役所まで行く手間を考えると、この場での確認は重要です）。
####  複数回計測の取り扱い
run_idを1, 2, 3と振り、同じCSVファイル内で複数回分のデータを区別します。SDカードへの書き込みはアプリ起動中（電源ON〜OFFまで）同じファイルに追記し続け、run_idで実験回を分ける形にします。

#### 注意点・リスク
エレベーターの待機列や混雑で、計測ボタンを押すタイミングがずれる可能性があります。誤操作時は再度ボタンを押せばアイドルに戻せる設計（前回確定済み）なので、操作ミス自体は致命的ではありません
展望台のエレベーターが直通でない場合（途中階で停止する可能性）、降下が一区間で完結しない可能性があります。事前に「直通かどうか」を確認しておくと安心です

# 補足: Windows11上で可視化(Python pandas)
pip install pandas matplotlib seaborn notebook ipykernel今回インストールしていただく5つのライブラリは、データ分析と可視化を行うための必須のツールセットです。それぞれの役割と関係性を解説します。
## 1. pandas（パンダス）

* 役割: データの読み込み・加工・管理
* 説明: センサーデータ分析の主役となるライブラリです。CSVやExcelなどのデータを、Excelのシートのような「縦横の表形式（データフレーム）」として読み込みます。膨大なセンサーデータから「特定の時間帯だけを抜き出す」「異常値（ノイズ）を取り除く」「1分ごとの平均値にまとめる」といった処理を、高速かつ簡単なコードで行うことができます。

## 2. matplotlib（マットプロットリブ）

* 役割: グラフ描画の土台（基本機能）
* 説明: Pythonでグラフを描くための最も歴史があり、広く使われている標準的なライブラリです。折れ線グラフ、散布図、棒グラフなど、ほぼ全ての種類のグラフを描画できます。グラフのサイズ、軸のラベル、色、フォントなどの細かいデザインを自由自在にカスタマイズできます。

## 3. seaborn（シーボーン）

* 役割: グラフを美しく、高度に可視化する
* 説明: matplotlib の機能をベースに作られた、より洗練されたグラフを作るためのライブラリです。matplotlib だけだと地味になりがちなデザインを、数行のコードで自動的にモダンで綺麗な色合いにしてくれます。また、「複数のセンサーデータの相関関係を一覧にする」といった、統計的な一歩進んだ可視化が得意です。

## 4. notebook（ノートブック）

* 役割: ツールを動かす裏方のシステム（本体）
* 説明: 本来、Webブラウザ上でJupyter Notebookの仕組みを動かすためのコア（中心）となるプログラムです。VS Codeでノートブック機能（.ipynbファイル）を開いて操作するために、PCのシステム側で必要となるためインストールします。

## 5. ipykernel（アイピーカーネル）

* 役割: VS CodeとPythonを繋ぐ通訳（実行エンジン）
* 説明: VS Code上で書いたプログラムのコードを、Pythonに渡して実行させ、その結果（計算結果やグラフ）を再びVS Codeの画面上に戻して表示するための「架け橋」となるプログラムです。これがないと、VS Code上でノートブックの再生ボタン（三角マーク）を押してもコードが動きません。
